Multiplayer Backend

An ASP.NET Core backend built to exercise the parts of backend engineering that matter beyond CRUD: authenticated ownership, relational persistence, optimistic concurrency, distributed cache and queue state, dependency health, containerized infrastructure and integration testing against real PostgreSQL and Redis instances.

System architecture

The backend is deliberately small enough to understand as one system, but it crosses the boundaries that make backend work interesting: HTTP/API behavior, identity, persistence, concurrent writes, distributed state, infrastructure dependencies and end-to-end tests.

Authenticated client │ ▼ ASP.NET Core Minimal API │ ├── JWT authentication / claims │ ├── Player endpoints │ ├── EF Core ─────────────► PostgreSQL │ └── distributed cache ───► Redis │ ├── Inventory endpoints │ └── EF Core ─────────────► PostgreSQL │ └── optimistic concurrency │ ├── Login queue │ └── StackExchange.Redis ─► Redis sorted set │ └── Lua atomic join │ └── Health checks ├── /health/live └── /health/ready ───────► PostgreSQL + Redis

What is actually implemented

  • Account registration and login with password hashing and JWT bearer authentication.
  • Authenticated /me endpoints that derive player identity from token claims.
  • PostgreSQL persistence through Entity Framework Core.
  • Redis cache-aside reads for player state with a bounded TTL.
  • A Redis sorted-set login queue with an atomic Lua join operation.
  • Inventory stacking and player-to-player transfers.
  • Optimistic inventory concurrency using an EF row-version property backed by PostgreSQL.
  • Separate liveness and dependency-readiness health checks.
  • Docker Compose development infrastructure.
  • Integration tests using WebApplicationFactory and disposable PostgreSQL/Redis Testcontainers.
The important part of this case study is not the technology list. The sections below link each claim to the actual implementation and show the behavior being tested.

Deep dive: atomic Redis login queue

The problem

Queue state cannot live only inside one API process if multiple backend instances need to observe the same queue. Redis provides shared state, but a join operation itself still contains several dependent steps.

Join(account) │ ├── Is this account already queued? │ ├── Allocate the next sequence number │ ├── Add account to the sorted set │ └── Return its current rank If these are separate round trips, concurrent joins can interleave between steps.

The implementation

The queue uses a Redis sorted set. A monotonically increasing sequence becomes the score, which preserves join order. The check, sequence allocation, insertion and rank calculation run inside one Lua script so the operation is atomic from Redis' point of view.

local rank = redis.call('ZRANK', KEYS[1], ARGV[1]) if rank then return rank + 1 end local sequence = redis.call('INCR', KEYS[2]) redis.call('ZADD', KEYS[1], sequence, ARGV[1]) rank = redis.call('ZRANK', KEYS[1], ARGV[1]) return rank + 1

The behavior is tested concurrently

The integration test does not merely call the endpoint once. It authenticates a real test account and submits 20 concurrent join requests for the same account. Every response must report position 1, and the final queue must still contain exactly one member.

var tasks = Enumerable.Range(0, 20) .Select(_ => client.PostAsync( "/api/login-queue/join", null)) .ToArray(); var responses = await Task.WhenAll(tasks); // each response reports position 1 // final queue count == 1

Deep dive: inventory writes and optimistic concurrency

The problem

A transfer is not just “subtract here, add there.” The source quantity can become stale if another request modifies the same inventory row after it was read but before the write is committed.

Initial state: 10 Health Potions Request A reads 10 ──► transfer 8 Request B reads 10 ──► transfer 6 Without concurrency detection, a stale write can overwrite newer state. With optimistic concurrency: one write commits stale writer detects a version mismatch API can return 409 Conflict instead of silently overwriting state

Database concurrency token

InventoryItem.Version is configured as an EF row-version property. The transfer service catches DbUpdateConcurrencyException and returns a domain-level concurrency result, which the HTTP endpoint maps to 409 Conflict.

modelBuilder.Entity<InventoryItem>() .Property(item => item.Version) .IsRowVersion(); ... try { await _db.SaveChangesAsync(); } catch (DbUpdateConcurrencyException) { return TransferItemResult.ConcurrencyConflict; }

Redis cache-aside player reads

GET /api/players/me checks the distributed Redis cache first. A cache miss falls through to a projected PostgreSQL query, then stores the serialized response in Redis for five minutes before returning it.

Integration tests use real infrastructure

The test suite does not replace PostgreSQL and Redis with in-memory substitutes. The shared fixture creates disposable PostgreSQL and Redis containers, injects their connection strings into the application, applies the same EF migrations, and runs requests through WebApplicationFactory<Program>.

Operational behavior

Liveness and readiness are intentionally different. Liveness only answers whether the application process can serve a request. Readiness includes PostgreSQL and Redis checks, so an orchestrator can keep an unhealthy instance out of service without treating every dependency interruption as a dead process.

GET /health/live └── process is responding GET /health/ready ├── PostgreSQL ready? └── Redis ready?

Run it locally

The development stack is reproducible with Docker Compose. Secrets are supplied through a local .env file rather than committed configuration.

# .env POSTGRES_PASSWORD=devpassword JWT_SIGNING_KEY=<base64-key> # start API + PostgreSQL + Redis docker compose up --build # verify health curl http://localhost:5035/health/live curl http://localhost:5035/health/ready # run integration tests dotnet test MultiplayerBackend.Api.Tests/MultiplayerBackend.Api.Tests.csproj

Scope and limitations

This is an independent engineering project, not a production service with real users or production traffic. The point is to make backend mechanisms concrete and inspectable: authentication, ownership, persistence, distributed state, concurrency handling, infrastructure health and integration testing. The public repository contains the implementation so those claims can be verified directly rather than taken from a portfolio description.
