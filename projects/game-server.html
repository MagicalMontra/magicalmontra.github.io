Authoritative Game Server

A Linux/C++20 multiplayer-server project built to expose the networking and simulation mechanisms that higher-level game networking frameworks normally hide: file-descriptor ownership, non-blocking I/O, stream framing, authoritative time, sub-tick events, rollback/resimulation, stable entity identity, sparse spatial indexing and replication interest.

View source on GitHub Architecture notes

What works now

This is not presented as a finished production server. The current repository has a working systems foundation and simulation prototype, with temporary in-process demonstrations for rollback and interest behavior while the real connection-to-entity and movement-packet path is still being built.

  • Linux TCP listener with non-blocking client sockets.
  • Level-triggered epoll event loop.
  • timerfd integrated into the same event loop for authoritative simulation ticks.
  • RAII ownership of Linux file descriptors through a move-only UniqueFd.
  • Explicit TCP packet framing and a stream decoder that handles partial frames.
  • Per-client buffered writes with partial-send / EAGAIN handling.
  • Authoritative GameTime independent from tick identity.
  • Sub-tick simulation events and bounded rollback/resimulation history.
  • Replayable movement, spawn and despawn events.
  • Stable EntityId identity with dense entity storage.
  • Sparse chunked spatial indexing with dense 1D cells inside each chunk.
  • Incremental AOI updates during normal simulation and full derived-index rebuild after rollback restore.
  • Per-observer interest diffing into entered, stayed and left.
Current boundary: rollback is demonstrated with replayable server-side events, but real network movement commands and replication snapshots are the next vertical-slice milestone. UDP, clock synchronization and client prediction/reconciliation come after that.

Deep dive: Linux resource ownership

The problem

Sockets, the epoll instance and the timerfd are all integer file descriptors. Raw integers do not express ownership, and early returns or future exceptions make manual cleanup easy to get wrong.

Move-only RAII

UniqueFd is the ownership primitive. Copying is deleted so two objects cannot believe they own the same descriptor. Moving transfers ownership, and destruction closes the descriptor.

class UniqueFd { public: explicit UniqueFd(int fd = -1) noexcept; ~UniqueFd(); UniqueFd(const UniqueFd&) = delete; UniqueFd& operator=(const UniqueFd&) = delete; UniqueFd(UniqueFd&& other) noexcept; UniqueFd& operator=(UniqueFd&& other) noexcept; private: int fd_; };

Deep dive: one event loop for networking and simulation

The server puts the listening socket, the simulation timerfd and connected clients into the same level-triggered epoll loop. The outer thread blocks in epoll_wait() until one of those file descriptors can make progress.

epoll_wait() │ ├── listener readable ─────► accept pending clients │ ├── timerfd readable ──────► advance authoritative simulation │ └── client readiness ├── EPOLLIN ───────► receive / decode packets └── EPOLLOUT ──────► flush pending send bytes

The tick source is a Linux timerfd using CLOCK_MONOTONIC. If the timer reports more than one expiration, the current implementation advances one authoritative step per expiration. A catch-up cap/overload policy is intentionally listed as follow-up work rather than hidden.

Deep dive: non-blocking writes are stateful

A writable socket does not guarantee that the full logical message can be sent. ClientConnection therefore owns a pending byte buffer and a send offset. It keeps calling send() while progress is possible, retains unsent bytes on EAGAIN/EWOULDBLOCK, retries EINTR, and reports whether output is complete or still pending.

while (send_offset_ < send_buffer_.size()) { sent = socket_.Send(remaining); sent > 0 → advance offset EAGAIN / EWOULDBLOCK → keep remaining bytes for later EPOLLOUT EINTR → retry other error → fail connection }

Deep dive: TCP is a byte stream, not a packet transport

One recv() call is not assumed to correspond to one application packet. The wire format has an explicit six-byte header and the decoder accumulates arbitrary stream fragments until a complete frame exists.

wire frame [ uint32 payload_size ][ uint16 packet_type ][ payload ] 4 bytes 2 bytes TCP may deliver: recv #1 [header part] recv #2 [rest header + payload part] recv #3 [rest payload + next packet] PacketDecoder retains bytes until an entire frame is available.

The decoder converts header fields from network byte order, rejects payload sizes above its configured maximum, advances a read offset without erasing the vector after every packet, and compacts consumed space only when useful.

Authoritative time is not the same thing as tick identity

The current experiment deliberately runs the authoritative server at 12 Hz. The design does not require a future client prediction step to map 1:1 to a server tick. Instead, events are placed on an authoritative simulation-time axis represented by std::chrono::nanoseconds.

using GameTime = std::chrono::nanoseconds; struct SimulationStep { std::uint64_t tick; GameTime start_time; GameTime end_time; GameTime delta_time; };

This distinction matters at rates such as 12 Hz: one ideal step is 83.333… ms, which cannot be represented exactly as an integer number of nanoseconds. The timer interval itself is necessarily truncated, but the authoritative game-time boundary is derived from the absolute tick index rather than repeatedly adding that truncated period.

whole_seconds = tick / tick_rate remainder_ticks = tick % tick_rate remainder_nanoseconds = remainder_ticks * 1,000,000,000 / tick_rate GameTime = whole_seconds + remainder_nanoseconds At 12 Hz: Tick 12 → exactly 1.000000000 s on authoritative GameTime

Sub-tick events

A 12 Hz outer simulation loop does not force all gameplay input to 83 ms timing buckets. Each simulation step covers [start_time, end_time), and the simulation can split that interval around an event timestamp.

Server step 1.500 s -------------------------------- 1.583 s ↑ 1.550 s movement event simulate old state: 1.500 → 1.550 apply event: @ 1.550 simulate new state: 1.550 → 1.583

WorldSimulation::SimulateStep walks events in chronological order, integrates up to each exact event time, applies the event, then continues through the remainder of the server step.

Deep dive: bounded rollback and deterministic replay

Historical state

StateHistory<T, Capacity> is a fixed-size ring. The physical slot comes from tick % Capacity, but every stored entry also records the logical tick. That extra check prevents an overwritten slot from being mistaken for the requested historical state.

index = tick % Capacity slot contains: stored tick stored state Find(requested_tick): slot empty → not available stored tick != request → overwritten / stale otherwise → valid historical state

Replayable event timeline

Rollback is not movement-only. The canonical event timeline uses a std::variant payload for movement, player spawn and entity despawn. Events carry both GameTime and a stable order value, so events sharing the same timestamp still have deterministic ordering.

SimulationEvent ├── GameTime time ├── uint64 order └── variant payload ├── MovementInput ├── SpawnPlayerEvent └── DespawnEntityEvent

Rollback procedure

late event arrives │ ▼ find historical step containing event time │ ▼ restore state before that step │ ▼ rebuild derived SpatialGrid │ ▼ replay exact historical SimulationSteps + events │ ▼ overwrite stale history with corrected states │ ▼ corrected present

The repository currently demonstrates this with a deliberately late movement event. Player 1 initially moves forward. At server time 2.0 s, the simulation inserts a Backward event whose authoritative time is 1.55 s. The simulation restores the historical state, replays the interval around 1.55 s, and corrects the present position.

before correction @ 2.000 s x ≈ 2.0 late event says: Backward @ 1.550 s restore @ 1.500 s x = 1.5, Forward Forward 1.500 → 1.550 Backward 1.550 → 2.000 corrected present x ≈ 1.1

A second demonstration inserts a player-spawn event late, showing why entity lifecycle itself must be replayable rather than treated as an irreversible side effect outside the simulation timeline.

Stable entity identity vs dense storage

The simulation does not use a vector index as long-lived entity identity. EntityId remains stable while EntityStore<T> combines a dense std::vector for iteration with an ID-to-index hash map for average O(1) lookup. Removal uses swap-and-pop and repairs the moved entity's mapping.

stable identity EntityId = 42 │ ▼ unordered_map<EntityId, index> │ ▼ dense vector [ 7 ][ 42 ][ 19 ][ 88 ] remove 42: move last element into its slot repair 88 → new index pop_back() EntityId remains identity; vector index is only storage location.

Deep dive: sparse world, dense local spatial storage

The AOI grid is sparse at world scale but deliberately contiguous inside a loaded chunk. Global chunks live in an unordered_map; each chunk contains a fixed 16 × 16 logical grid represented as 256 physical 1D entries.

global world unordered_map<ChunkCoord, Chunk> only populated chunks exist Chunk 16 × 16 logical cells │ ▼ std::array<vector<EntityId>, 256> local flattening: index = y * 16 + x (0,0) → 0 (15,0) → 15 (0,1) → 16 (5,3) → 53 (15,15) → 255

Negative coordinates are handled mathematically

C++ integer division truncates toward zero, which is wrong for chunk addressing on the negative side of the world. The grid therefore uses explicit floor division and positive modulo.

global cell x = -17 chunk width = 16 C++ -17 / 16 → -1 (truncates toward zero) required chunk → -2 required local x → 15 result: chunk -2, local cell 15

Normal movement is incremental

A normal movement update first computes the new grid address. If the entity remains in the same cell, the membership data is untouched. Crossing a cell boundary removes the ID from the old cell with swap-and-pop and inserts it into the new one. Empty chunks are released.

entity moves │ ▼ compute new GridAddress │ ├── same cell ─────────► no membership mutation │ └── different cell ├── swap-and-pop from old cell ├── remove empty old chunk if necessary └── push into new cell rollback restore is different: restore WorldState → rebuild SpatialGrid once → replay incrementally

Neighborhood query results are sorted before leaving the spatial layer so internal hash-map/chunk iteration order does not leak into externally visible replication ordering.

Three different kinds of state

One of the central architectural decisions is that not everything associated with the simulation belongs in a rollback snapshot.

1. Authoritative simulation state WorldState → canonical game state → saved and restored during rollback 2. Derived simulation state SpatialGrid → reconstructed from WorldState → rebuilt after historical restore 3. Replication knowledge InterestTracker → what a remote observer is currently considered to know → NOT rewound during simulation rollback

Rewinding replication knowledge would imply that the server could unsend packets a client has already received. Instead, rollback corrects the authoritative present, and the next replication diff tells the client how that corrected present differs from what it currently knows.

Interest tracking: entered, stayed, left

InterestTracker receives the newly desired AOI set, sorts and deduplicates it, then performs a merge-style single pass against the previous sorted set.

previous interest: [2, 4, 7] new desired: [4, 7, 9] merge diff: 2 → left 4 → stayed 7 → stayed 9 → entered future replication mapping: entered → SpawnEntity stayed → StateUpdate left → DespawnEntity

Authority model

The intended network contract is that clients send intent, not authoritative outcomes. A future movement packet may describe direction plus sequence/timing metadata; it should not submit a trusted position, displacement, movement speed or client-provided delta time. The server owns authoritative time and state transitions.

client may send Forward / Backward / Left / Right Attack / Dodge / Parry / Jump sequence + timing metadata client does NOT own authoritative position movement displacement server delta time damage / hit result parry result

Why 12 Hz does not mean 83 ms input precision

The server rate is intentionally low as an experiment. That outer cadence controls how often the authoritative loop advances, but event timestamps can still split a step internally. A future client may predict at 30/60 Hz while the server stays at a lower rate; shared GameTime is the bridge rather than matching tick numbers.

possible cadence separation server simulation 12 Hz snapshot replication 6 Hz (future independent cadence) client prediction 60 Hz (future client) rendering unrestricted These rates do not need to share tick identity.

Build and run

The game-server target is Linux-specific and built with CMake/C++20. From the repository root on Linux or WSL:

cmake -S MultiplayerBackend.GameServer \ -B MultiplayerBackend.GameServer/build cmake --build MultiplayerBackend.GameServer/build ./MultiplayerBackend.GameServer/build/multiplayer_game_server

The current main.cpp starts the server on TCP port 7777 with a 12 Hz authoritative simulation rate.

What is deliberately not claimed yet

The project page should make it possible to distinguish implemented systems from the roadmap. These are important follow-ups, but they are not presented as completed features:

  • ReplicationSnapshot data model and serialized spawn/update/despawn snapshots.
  • Real connection/session/player → controlled EntityId ownership.
  • Real movement commands arriving from a network client and triggering late-input rollback.
  • Independent replication cadence.
  • UDP path for latency-sensitive gameplay.
  • Client/server clock synchronization and timestamp validation.
  • Prediction/reconciliation on an actual client.
  • Rollback-sensitive Attack/Dodge/Parry combat.
  • Explicit EPOLLERR/EPOLLHUP policy and per-client pending-send limits.
  • A capped timer catch-up/overload policy.
Next portfolio milestone: InterestDelta → ReplicationSnapshot, real connection-to-entity ownership, movement command packets, then a real late network input that restores history, resimulates and produces a corrected replicated present.

Scope

This is an independent systems-learning project, not a production server with live traffic. Its purpose is to make the mechanisms explicit and inspectable rather than hiding them behind a networking framework. The repository and architecture notes are public so the implementation, current limitations and design reasoning can be checked directly.
