Independent systems project

Authoritative Game Server

A Linux/C++20 multiplayer-server project built to understand the lower-level networking and simulation mechanisms normally hidden behind game networking frameworks.

Current architecture

Linux GameServer │ ├── non-blocking TCP ├── epoll ├── timerfd ├── framed protocol │ ├── WorldSimulation │ ├── authoritative GameTime │ ├── replayable SimulationEvent timeline │ ├── bounded StateHistory │ └── rollback / resimulation │ ├── SpatialGrid │ ├── sparse chunks │ └── dense 1D cell indexing │ └── InterestTracker ├── entered ├── stayed └── left

Why client and server ticks do not match

The server deliberately experiments with a relatively low authoritative simulation rate while allowing a client to predict at a higher rate. Commands are positioned on a shared authoritative game-time timeline rather than requiring client tick N to correspond to server tick N.

Sub-tick events and rollback

A command may belong partway through a coarse server step. The simulation can integrate the previous control state up to the event time, apply the event, then simulate the remainder. Late events restore a historical world state and replay the stored event/step history back to the present.

Three kinds of state

Authoritative WorldState └── restored during rollback Derived SpatialGrid └── rebuilt from WorldState when needed Replication InterestTracker └── what the remote client currently knows └── never rewound with simulation rollback

Spatial representation

The world uses sparse chunks so an entire theoretical map is not allocated. Inside each loaded chunk, local cells are stored as one contiguous 1D array using index = y * width + x. Negative world coordinates are handled explicitly with floor division and positive modulo.
