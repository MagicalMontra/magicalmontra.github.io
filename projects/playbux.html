Deep dive: custom grid-based Area of Interest

The problem

In a larger multiplayer world, sending every networked entity to every connected player does unnecessary work on both the server and client. Replication needs a relevance rule: which entities should a particular observer know about now?

The approach

I implemented a custom grid-based AOI and integrated it with Mirror. World positions were spatially partitioned so the server could derive a nearby/relevant entity set for each observer and use that set to control selective synchronization.

authoritative world state │ ▼ entity positions │ ▼ custom spatial grid │ ├── observer location └── nearby/relevant cells │ ▼ relevant entities │ ▼ Mirror visibility / interest │ ▼ selective synchronization

The important architectural distinction is that the spatial structure answers a replication question. The authoritative world still owns the entity state; the AOI determines which subset is relevant to a given client.

Why a grid

The grid avoids repeatedly comparing every observer against every entity in the world. Instead, the server can reason about spatial neighborhoods first and narrow the candidate set before replication work is performed.

naive relevance search observer × every entity in world versus grid relevance search observer position ↓ observer cell / neighborhood ↓ entities already partitioned into nearby cells ↓ replication candidates

I am intentionally not publishing exact production constants, internal class names or former-employer code. The point of this diagram is to document the architecture I worked on, not reconstruct the source repository from memory.

Deep dive: server-authoritative movement

Movement was designed around server authority: the client could provide responsive local feedback, but it was not the final authority on world position. The server owned the accepted movement state and could correct the client's predicted result.

local player input │ ├──────────────────────► local prediction │ │ │ ▼ │ immediate response │ └──► network command │ ▼ authoritative server │ ├── process movement └── authoritative state │ ▼ client receives state │ ▼ reconciliation │ ┌─────────┴─────────┐ │ │ prediction close prediction differs │ │ continue correct / converge

Why prediction was necessary

Waiting for a network round trip before showing local movement would make control feel delayed. Prediction lets the client respond immediately while keeping the server authoritative. Reconciliation then deals with disagreement between predicted local state and the server's accepted state.

My multiplayer work was not limited to movement and visibility. I also worked on server-side systems around player spawning, combat and state shared between connected players.
